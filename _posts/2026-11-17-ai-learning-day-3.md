# AI Learning Day 3 - 좋은 프롬프트를 구성하는 요소와 개선 방법

## 1. 학습 목표

Day 3에서는 좋은 프롬프트를 구성하는 요소를 이해하고, 실제 Unity 개발 상황을 가정해 프롬프트를 작성하고 개선하는 실습을 진행했다.

또한 동일한 주제에 대해 서로 다른 프롬프트를 사용했을 때 AI의 답변이 어떻게 달라지는지 비교했다.

이번 학습의 목표는 다음과 같다.

1. 프롬프트를 구성하는 주요 요소 이해하기
2. Role, Task, Context, Constraints, Output Format 활용하기
3. 작성한 프롬프트의 부족한 부분을 찾아 개선하기
4. 동일한 요청에 대한 프롬프트별 답변 비교하기
5. AI가 작성한 코드와 설계를 검증하는 방법 생각하기

---

## 2. 좋은 프롬프트를 구성하는 다섯 가지 요소

### 2-1. Role (역할)

AI가 어떤 관점에서 답변할지 지정하는 요소다.

예를 들어 다음과 같이 작성할 수 있다.

- Unity 게임 개발을 가르치는 강사
- C# 프로그래밍을 가르치는 강사
- 소프트웨어 설계 전문가

역할을 지정하면 답변의 관점이나 설명 방식을 유도할 수 있다.

다만 역할을 지정했다고 해서 AI의 전문성이나 답변의 정확성이 보장되는 것은 아니다.

### 2-2. Task (작업)

AI에게 정확히 무엇을 요청할지 지정하는 요소다.

예를 들어 단순히 "오브젝트 풀링을 알려줘"라고 요청하는 것보다 다음과 같이 작성하는 편이 명확하다.

"오브젝트 풀링의 개념과 Unity 적용 방법을 설명해 줘."

### 2-3. Context (맥락)

AI가 답변을 작성하는 데 필요한 상황과 배경 정보를 전달하는 요소다.

예를 들어 다음과 같은 정보가 있다.

- Unity 6 사용
- C# 기반의 2D 게임 개발
- 적 공격과 폭발 효과에 Instantiate와 Destroy를 반복 사용

이러한 정보를 제공하면 AI가 일반적인 개념 설명에서 벗어나 현재 개발 상황에 맞는 답변을 제공하는 데 도움이 된다.

### 2-4. Constraints (제약 조건)

답변을 작성할 때 지켜야 할 조건이나 제한 사항을 지정하는 요소다.

예를 들어 다음과 같다.

- 게임 개발 초보자가 이해할 수 있도록 설명
- 기존 Instantiate/Destroy 방식과 비교
- 불필요한 최적화 효과를 단정하지 않기

AI가 특정 방향으로만 답변하거나 확인되지 않은 장점을 과장하지 않도록 범위를 제한할 수 있다.

### 2-5. Output Format (출력 형식)

AI가 어떤 순서와 형태로 답변할지 지정하는 요소다.

예를 들어 다음과 같이 요청할 수 있다.

1. 개념
2. 필요한 이유
3. 기존 방식과 비교
4. C# 예제
5. 주의 사항

출력 형식을 지정하면 답변을 이해하거나 이후에 다시 확인하기 쉬워진다.

### 정리

다섯 가지 요소를 항상 전부 사용해야 하는 것은 아니다.

요청의 목적과 복잡도에 따라 필요한 요소만 선택하면 된다. 중요한 것은 프롬프트의 길이가 아니라 원하는 결과를 얻는 데 필요한 정보를 전달하는 것이다.

## 3. 실습 1: 오브젝트 풀링 학습 프롬프트 작성

### 3-1. 실습 상황

Unity 6과 C#으로 2D 게임을 개발하고 있다고 가정했다.

적 공격이나 폭발 효과를 구현할 때 Instantiate와 Destroy를 반복해서 사용하고 있으며, 오브젝트 풀링의 개념과 적용 방법을 학습하고자 했다.

### 3-2. 내가 작성한 프롬프트

```text
[Role]
Unity 게임 개발을 가르치는 강사

[Task]
오브젝트 풀링의 개념과 Unity 적용 방법 설명

[Context]
Unity 6과 C# 기반의 2D 게임이며, 적 공격과 폭발 효과에 Instantiate와 Destroy를 반복 사용하고 있음

[Constraints]
초보자가 이해할 수 있도록 설명하고, 기존 Instantiate/Destroy 방식과 비교하며, 불필요한 최적화 효과를 단정하지 않기

[Output Format]
1. 개념 2. 필요한 이유 3. 기존 방식과 비교 4. C# 예제 5. 주의 사항

[추가 요청]
코드에 주석을 달아줘.
```

### 3-3. 작성한 프롬프트 평가

이번 프롬프트는 다섯 가지 구성 요소를 모두 활용했다.

특히 Context와 Constraints를 구체적으로 작성한 점이 좋았다.

- 현재 개발 환경과 사용 기술을 전달했다.
- 실제 게임에서 어떤 상황에 적용하려는지 설명했다.
- 초보자 수준의 설명을 요청했다.
- 최적화 효과를 무조건적으로 단정하지 않도록 제한했다.

단순히 오브젝트 풀링의 개념을 알려 달라고 요청하는 것보다 원하는 답변의 방향이 명확해졌다.

### 3-4. 프롬프트 개선하기

작성한 프롬프트를 다시 살펴보니 C# 예제의 구체적인 범위가 부족하다고 생각했다.

단순히 C# 예제를 요청하면 AI가 지나치게 복잡한 구조를 제시할 수도 있다.

또한 오브젝트 풀링은 객체를 생성하는 것뿐 아니라 사용이 끝난 객체를 반환하고, 다시 사용할 때 이전 상태를 초기화하는 과정도 중요하다.

따라서 다음 내용을 추가하기로 했다.

- 처음에는 이해하기 쉬운 간단한 구조로 예제를 작성할 것
- 객체를 풀에 반환하는 시점 설명
- 객체를 재사용할 때 초기화해야 할 상태 설명
- 코드 실행 흐름 설명

**개선한 프롬프트**

```text
[Role]
Unity 게임 개발을 가르치는 강사

[Task]
오브젝트 풀링의 개념과 Unity 적용 방법 설명

[Context]
Unity 6과 C# 기반의 2D 게임이며, 적 공격과 폭발 효과에 Instantiate와 Destroy를 반복 사용하고 있음

[Constraints]
- 게임 개발 초보자가 이해할 수 있도록 설명할 것
- 기존 Instantiate/Destroy 방식과 오브젝트 풀링 방식을 비교할 것
- 불필요한 최적화 효과를 단정하지 말고, 장단점을 함께 설명할 것
- 처음에는 이해하기 쉬운 간단한 구조로 예제를 작성할 것
- 객체를 풀에 반환하는 시점과 재사용할 때 초기화해야 할 상태를 설명할 것
- 코드의 각 주요 부분에 주석을 작성할 것

[Output Format]
1. 오브젝트 풀링의 개념
2. 오브젝트 풀링이 필요한 이유
3. Instantiate/Destroy 방식과 비교
4. Unity 6과 C#을 활용한 간단한 구현 예제
5. 코드의 동작 과정 설명
6. 객체 반환 및 재사용 시 주의 사항
7. 실제 게임 프로젝트에 적용할 때 고려할 점

[추가 요청]
코드에 주석을 달아주고, 초보자가 코드를 따라가며 이해할 수 있도록 실행 흐름도 설명해 줘.
```

**개선 전후 비교**

| 항목 | 기존 프롬프트 | 개선 프롬프트 |
|---|---|---|
| C# 예제 | C# 예제 요청 | 간단한 구조의 구현 예제 요청 |
| 코드 주석 | 주석 요청 | 주요 코드에 주석 요청 |
| 주의 사항 | 일반적인 주의 사항 | 반환 시점과 재사용 초기화 명시 |
| 설명 방식 | 개념과 적용 방법 | 코드 실행 흐름까지 설명 |

이번 개선에서 중요한 점은 단순히 조건을 많이 추가한 것이 아니다.

AI가 무엇을 설명해야 하는지뿐만 아니라, 내가 이해하기 위해 어떤 설명이 필요한지도 전달했다는 점이다.

## 4. 실습 2: 프롬프트에 따른 AI 답변 비교

이번에는 Unity Addressables를 주제로 세 가지 프롬프트를 작성하고 답변을 비교했다.

목표는 프롬프트의 구성 방식에 따라 AI가 제공하는 답변이 어떻게 달라지는지 확인하는 것이다.

### 4-1. 실험 주제

기존 Unity 프로젝트에서는 Resources.Load를 사용해 리소스를 불러왔다.

이번에는 Addressables를 학습하고자 했으며, 동일한 학습 주제를 서로 다른 프롬프트로 요청했다.

### 4-2. 1번 프롬프트: 최소한의 요청

**요청 내용**

```text
Unity Addressables 사용법을 알려줘.
```

**답변 특징**

짧은 요청이었지만 상당히 상세한 학습 자료를 제공했다.

주요 내용은 다음과 같다.

- Addressables의 개념과 Resources.Load 비교
- Addressables 설치 및 에셋 등록
- LoadAssetAsync와 InstantiateAsync
- AsyncOperationHandle과 Release
- Addressables와 Object Pooling의 연계
- 학습 확인 문제와 다음 학습 방향

특히 별도로 요청하지 않았음에도 학습 순서를 구성하고, Object Pooling과의 연계까지 설명했다.

짧은 프롬프트만으로도 AI가 사용자의 학습 목적을 상당 부분 추론해 답변했다는 점이 인상적이었다.

### 4-3. 2번 프롬프트: 역할과 맥락 제공

**요청 내용**

```text
너는 Unity 게임 개발 강사야.

Unity 6으로 2D 게임을 개발하고 있어.
기존에는 Resources.Load로 리소스를 불러왔는데
Addressables를 학습하고 싶어.

초보자도 이해할 수 있도록 사용법을 설명해 줘.
```

**답변 특징**

이번에는 AI에게 역할과 개발 환경, 학습 목적을 전달했다.

답변은 다음과 같은 내용을 포함했다.

- Resources.Load와 Addressables의 차이
- Addressables 설치 및 초기 설정
- 에셋 등록과 주소 지정
- InstantiateAsync를 활용한 생성
- LoadAssetAsync와 Coroutine을 활용한 비동기 로딩
- AsyncOperationHandle과 Release
- Addressables 콘텐츠 빌드
- 실습 과제와 다음 학습 순서

1번과 비교하면 실제 Unity 6의 2D 게임 개발 상황을 가정한 학습 자료라는 점이 더 명확해졌다.

### 4-4. 3번 프롬프트: 조건과 출력 형식 구체화

**요청 내용**

```text
너는 Unity 게임 개발을 가르치는 강사야.

Unity 6으로 2D 게임을 개발하고 있어.
기존에는 Resources.Load로 리소스를 불러왔지만
Addressables를 학습하고 싶어.

다음 조건을 지켜 줘.
- Unity 초보자도 이해할 수 있게 설명할 것
- Resources.Load와 Addressables의 차이를 비교할 것
- 간단한 C# 코드 예제를 제공할 것
- 비동기 로딩과 리소스 해제도 설명할 것
- 확인되지 않은 기능이나 동작은 단정하지 말 것

다음 형식으로 답변해 줘.
1. 개념
2. 기존 방식과의 차이
3. 사용 방법
4. C# 코드 예제
5. 주의 사항
```

**답변 특징**

이번에는 학습 목표뿐 아니라 반드시 다뤄야 할 내용과 답변 형식을 지정했다.

주요 내용은 다음과 같다.

- Addressables의 개념
- Resources.Load와 Addressables의 차이
- Addressables 설치 및 에셋 등록
- LoadAssetAsync와 InstantiateAsync
- AsyncOperationHandle과 Result
- Release와 ReleaseInstance
- 비동기 작업 중 객체가 파괴되는 상황
- 실제 프로젝트 적용 시 주의 사항

특히 비동기 작업 중 컴포넌트나 씬이 파괴되는 상황까지 언급했다는 점이 눈에 띄었다.

### 4-5. 세 가지 답변 비교

| 비교 항목 | 1번 | 2번 | 3번 |
|---|---|---|---|
| 프롬프트 길이 | 매우 짧음 | 보통 | 상대적으로 김 |
| 역할 지정 | 없음 | 있음 | 있음 |
| 개발 환경 | 없음 | Unity 6, 2D | Unity 6, 2D |
| 학습 목적 | 간접적으로 추론 | 명시 | 명시 |
| 제약 조건 | 없음 | 초보자 설명 | 여러 조건 명시 |
| 출력 형식 | AI가 구성 | AI가 구성 | 직접 지정 |
| 답변 수준 | 상세함 | 상세함 | 상세함 |

### 4-6. 실험 결과와 느낀 점

솔직히 말하면 세 가지 답변 모두 만족스러웠다.

특히 1번 프롬프트는 단 한 문장으로 요청했음에도 학습에 필요한 내용을 상당히 체계적으로 제공했다.

처음에는 프롬프트를 구체적으로 작성할수록 더 좋은 결과를 얻을 것이라고 생각했다.

하지만 이번 실험에서는 프롬프트의 길이나 구성 요소의 개수가 답변의 품질을 반드시 결정하지는 않는다는 점을 확인했다.

물론 2번과 3번처럼 구체적인 정보를 제공하면 답변의 방향과 범위를 더 명확하게 유도할 수 있다.

다만 최신 AI는 사용자가 명시하지 않은 의도까지 상당 부분 추론하고, 필요한 설명을 스스로 보완할 수 있다는 점도 알게 됐다.

**이번 실험에서 얻은 핵심은 프롬프트가 길다고 무조건 좋은 답변을 얻는 것은 아니라는 점이다.**

## 5. AI가 제안한 설계를 어떻게 판단할까?

이번 실습에서는 프롬프트 작성뿐 아니라 AI가 작성한 코드와 설계를 어떻게 활용할 것인지도 생각해 봤다.

### 5-1. 기존 코드가 복잡하다면?

AI가 ObjectPool 클래스를 작성했는데 코드가 너무 복잡하고 이해하기 어렵다면 어떻게 해야 할까?

나는 우선 기존 코드의 구조를 유지하면서 각 클래스와 함수의 역할, 실행 순서를 설명해 달라고 요청할 것 같다.

다만 설명을 들어도 설계가 지나치게 복잡하거나 불필요하다고 판단한다면 새로운 구조로 변경하는 것도 고려할 수 있다.

### 5-2. AI 시대의 시스템 설계 변경

AI를 활용하면 기존 코드 분석, 새로운 설계안 작성, 반복적인 코드 수정 등의 비용을 줄일 수 있다고 생각한다.

따라서 기존 설계를 무조건 유지할 필요는 없다고 생각한다.

하지만 코드를 수정하는 비용과 시스템을 변경하는 비용은 다르다.

설계를 변경할 때는 다음과 같은 부분도 확인해야 한다.

- 기존 코드에서 해당 시스템을 사용하는 곳은 어디인가?
- 다른 시스템과의 의존성은 없는가?
- 변경으로 인해 기존 기능에 문제가 발생하지 않는가?
- 객체의 생성, 반환, 재사용 과정에서 오류가 발생하지 않는가?

AI가 코드를 수정해 줄 수는 있지만, 변경으로 인한 모든 영향을 정확하게 보장하는 것은 아니다.

결국 중요한 것은 설계를 변경할 수 있는 능력뿐 아니라, 언제 설계를 변경해야 하는지 판단하는 능력이라고 생각한다.

### 5-3. 실제 테스트의 중요성

AI가 기존보다 짧고 이해하기 쉬운 ObjectPool 코드를 작성했다고 가정해 보자.

코드가 간결해졌다는 사실만으로 정상적으로 동작한다고 판단할 수는 없다.

실제 프로젝트에서 다음 항목을 테스트해야 한다.

1. 객체가 정상적으로 생성되는가?
2. 사용이 끝난 객체가 풀에 정상적으로 반환되는가?
3. 반환된 객체를 다시 가져와 사용할 수 있는가?
4. 재사용할 때 이전 위치나 상태가 남아 있지 않은가?
5. 여러 번 반복해도 오류가 발생하지 않는가?

AI가 작성한 코드가 논리적으로 맞아 보이는지 확인하는 것에서 끝나는 것이 아니라, 내가 기대한 동작과 실제 동작이 일치하는지 검증해야 한다.

## 6. 프롬프트 엔지니어링은 앞으로도 중요할까?

이번 Addressables 실험을 진행하면서 한 가지 의문이 생겼다.

**AI가 발전할수록 프롬프트 엔지니어링의 중요성은 점점 줄어들지 않을까?**

세 가지 프롬프트를 비교했을 때, 짧은 요청만으로도 상당히 상세한 답변을 얻을 수 있었다.

그렇다면 앞으로 AI가 더 발전하면 사용자가 Role, Context, Constraints, Output Format 등을 직접 작성하지 않아도 원하는 결과를 얻을 수 있지 않을까?

개인적으로는 지금과 같은 형태의 프롬프트 엔지니어링은 점차 변화할 것이라고 생각한다.

### 6-1. 프롬프트 작성 기술은 점점 쉬워질 수 있다

과거에는 원하는 답변을 얻기 위해 역할과 맥락, 제약 조건, 출력 형식 등을 구체적으로 작성해야 했다.

하지만 AI가 발전하면서 사용자가 명시하지 않은 의도도 추론하고 필요한 정보를 보완하는 수준이 높아지고 있다.

이번 실험에서 1번 프롬프트가 좋은 사례였다.

단순히 "Unity Addressables 사용법을 알려줘"라고 요청했지만 학습 순서부터 코드 예제, 주의 사항, 다음 학습 방향까지 제안했다.

앞으로는 사용자가 프롬프트를 정교하게 작성해야 하는 상황이 줄어들 수 있다고 생각한다.

### 6-2. 문제를 정의하는 능력은 여전히 중요하다

다만 프롬프트를 잘 작성하는 것과 문제를 잘 정의하는 것은 서로 다른 능력이라고 생각한다.

예를 들어 다음 두 요청을 비교해 보자.

**요청 A**

```text
Addressables 사용법을 알려줘.
```

**요청 B**

```text
기존 Unity 프로젝트에서 Resources.Load를 Addressables로 변경하려고 해.

기존 ResourceManager 구조를 최대한 유지하면서
변경할 부분을 분석하고, 예상되는 문제와 테스트 방법을 제시해 줘.
```

두 요청은 요구하는 결과가 다르다.

특히 요청 B를 작성하려면 자신의 프로젝트 상황과 원하는 결과를 알고 있어야 한다.

AI가 내용을 추론할 수는 있지만 사용자가 제공하지 않은 실제 프로젝트의 구조와 요구사항까지 정확하게 알 수는 없다.

따라서 프롬프트 엔지니어링은 완전히 사라지기보다는 사용자가 직접 프롬프트 문장을 설계하는 기술에서 AI에게 일을 잘 맡기고 결과를 관리하는 능력으로 중심이 이동할 것이라고 생각한다.

## 7. AI를 활용하는 개발자에게 필요한 역량

이번 학습을 통해 AI를 활용하는 데 필요한 역량을 다시 생각해 봤다.

개인적으로 중요하다고 생각하는 역량은 다음과 같다.

1. **목표 정의:** 내가 원하는 결과가 무엇인지 명확하게 정의하고 전달하는 능력
2. **문제 해결 방향 설정:** 문제를 어떻게 해결할지 방향을 정하거나, 방향을 모른다면 AI에게 여러 해결 방법을 추천받는 능력
3. **결과 이해:** AI가 제안한 코드와 설계가 어떤 원리로 동작하는지 이해하는 능력
4. **결과 검증:** AI가 작성한 코드가 실제 환경에서 올바르게 동작하는지 확인하는 능력
5. **개선 방향 결정:** 검증 결과를 바탕으로 기존 설계를 유지하거나 수정할지 판단하는 능력

이 중에서도 나는 **AI가 작성한 코드와 설계를 검증하는 능력이 가장 중요할 것 같다.**

### 7-1. 검증 능력이 중요한 이유

AI가 코드를 작성하는 비용은 점점 낮아질 수 있다.

하지만 코드가 문법적으로 올바르거나 논리적으로 그럴듯하다고 해서 실제 게임에서 정상적으로 동작한다는 보장은 없다.

예를 들어 ObjectPool을 구현한다고 가정해 보자.

- 반환된 오브젝트의 이전 상태가 초기화되지 않음
- 이미 반환된 오브젝트가 다시 반환됨
- 여러 시스템에서 동시에 접근하면서 예상하지 못한 동작이 발생함
- 객체가 풀에 없는 상황에서 잘못된 참조가 발생함

이런 문제는 실제 프로젝트에 적용하고 테스트하는 과정에서 발견할 수 있다.

### 7-2. 검증 능력에도 단계가 있다

| 단계 | 검증 내용 | Unity 예시 |
|---|---|---|
| 1. 코드 검토 | 코드 자체에 문제가 없는가? | 메모리 누수, 잘못된 참조 |
| 2. 실행 검증 | 실제 환경에서 정상 동작하는가? | 오브젝트 생성 및 반환 테스트 |
| 3. 설계 검증 | 요구사항에 맞는 구조인가? | ObjectPool이 현재 게임 구조에 적합한가? |

특히 세 번째 단계가 중요하다고 생각한다.

AI가 완벽하게 동작하는 ObjectPool을 작성했다고 해도 게임에서 해당 객체가 거의 생성되지 않는다면 오히려 불필요한 복잡성을 추가한 것일 수 있다.

단순히 코드가 동작하는지 확인하는 것에서 끝나는 것이 아니라 그 코드가 정말 필요한지까지 판단할 수 있어야 한다.

## 8. 이번 학습을 통해 느낀 점

이번 Day 3에서는 처음으로 프롬프트의 구성 요소를 체계적으로 학습하고 실제로 프롬프트를 작성해 봤다.

또한 동일한 주제에 대해 세 가지 프롬프트를 사용하면서 AI의 답변을 비교했다.

실험을 통해 프롬프트를 구체적으로 작성하는 것이 답변의 방향을 조절하는 데 도움이 된다는 점을 확인했다.

하지만 동시에 짧은 요청만으로도 AI가 상당히 좋은 결과를 제공할 수 있다는 사실도 확인했다.

이 경험을 통해 프롬프트 엔지니어링 자체가 앞으로도 지금과 같은 형태로 중요할지 의문이 생겼다.

개인적으로는 AI가 발전할수록 프롬프트를 작성하는 기술보다는 문제를 정의하고, AI의 결과물을 이해하고 검증하는 능력이 더 중요해질 것이라고 생각한다.

앞으로는 AI에게 코드를 작성하도록 요청하는 능력뿐 아니라 결과물을 이해하고 테스트하며 개선 방향을 판단하는 능력을 함께 키우고 싶다.

이번 학습에서 기억할 내용은 다음과 같다.

- Role, Task, Context, Constraints, Output Format을 활용해 프롬프트 구성하기
- 현재 개발 상황과 학습 목적을 구체적으로 전달하기
- 원하는 설명 수준과 코드 형태 지정하기
- 프롬프트의 길이가 답변의 품질을 반드시 결정하지는 않는다는 점 이해하기
- 기존 설계를 유지할지 변경할지 판단하기
- AI가 제안한 코드와 설계를 실제 환경에서 검증하기
- AI 시대에는 문제 정의와 결과 검증 능력이 중요해질 수 있다는 점 생각하기

**이번 학습의 핵심은 AI에게 단순히 답을 요청하는 것이 아니라, 내가 원하는 결과를 정의하고 AI가 제공한 결과를 검증하는 것이다.**
