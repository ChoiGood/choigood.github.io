# AI Learning Day 4 - Context Engineering과 프로젝트 Context 관리

## 1. 학습 목표

Day 4에서는 Context Engineering을 이해하고, AI와 장기간 대화하거나 프로젝트를 진행할 때 필요한 정보를 어떻게 관리해야 하는지 학습했다.

이번 학습의 주요 목표는 다음과 같다.

1. Context Engineering의 개념 이해하기
2. Prompt와 Context의 차이 이해하기
3. Context의 양과 품질이 AI 답변에 미치는 영향 이해하기
4. 대화가 길어질 때 발생할 수 있는 문제 이해하기
5. 프로젝트 정보를 관리하고 새로운 대화에서도 이어서 활용하는 방법 익히기

## 2. Context Engineering이란?

지난 Day 3에서는 좋은 프롬프트를 구성하는 방법을 학습했다.

프롬프트가 AI에게 무엇을 요청할지 전달하는 방법이라면, Context Engineering은 AI가 요청을 제대로 수행할 수 있도록 필요한 정보를 제공하고 관리하는 방법이다.

예를 들어 Unity에서 Addressables를 학습하고 싶다고 요청하는 상황을 생각해 보자.

**Prompt**

```text
Unity Addressables 사용법을 알려줘.
```

**Context**

```text
Unity 6으로 2D 게임을 개발하고 있어.

기존에는 Resources.Load를 사용했지만
Addressables를 학습하고 싶어.

Unity 개발 경험은 있지만 Addressables는 처음 사용해.
비동기 로딩과 리소스 해제 방법을 중심으로 학습하고 싶어.
```

같은 요청이라도 프로젝트 환경, 기존에 사용하던 방식, 학습 수준 등의 정보가 제공되면 AI가 상황에 맞는 답변을 제공하기 쉬워진다.

다만 Prompt와 Context는 완전히 분리된 개념은 아니다. 프롬프트 자체도 AI가 답변을 생성할 때 참고하는 Context의 일부가 될 수 있다.

### 좋은 Context를 구성하는 정보

| 구분 | 설명 | 예시 |
|---|---|---|
| 목표 | 무엇을 하려는가? | Addressables 학습 |
| 배경 | 어떤 상황인가? | Unity 6, 2D 게임 |
| 현재 상태 | 어디까지 진행했는가? | Resources.Load 사용 중 |
| 제약 조건 | 지켜야 할 사항은? | 기존 코드 구조 유지 |
| 참고 자료 | 어떤 자료가 필요한가? | C# 코드, 오류 로그 |
| 진행 상황 | 이전에 무엇을 시도했는가? | 비동기 로딩 적용 후 오류 발생 |

중요한 점은 모든 정보를 제공하는 것이 아니라, 현재 작업에 필요한 정보를 선별해서 전달하는 것이다.

## 3. Context의 양과 품질

Context가 많을수록 반드시 좋은 답변이 나오는 것은 아니다.

LLM은 Context Window라는 제한된 공간 안에서 정보를 참고해 답변을 생성한다.

Context Window에는 프롬프트뿐 아니라 이전 대화, 참고 자료 등 다양한 정보가 포함될 수 있다.

따라서 불필요한 정보가 너무 많거나 서로 충돌하는 정보가 포함되면 오히려 중요한 내용이 묻힐 수 있다.

예를 들어 다음과 같은 상황을 생각해 볼 수 있다.

- 이전에는 Resources.Load를 사용했지만 현재는 Addressables로 변경했다.
- 이전 코드와 수정된 코드가 모두 대화에 남아 있다.
- AI가 어느 코드가 최신 버전인지 알지 못한다.

이 경우 AI가 이전 코드를 기준으로 답변할 가능성이 있다.

결국 Context 관리에서 중요한 것은 단순히 정보를 많이 제공하는 것이 아니라 다음과 같은 기준을 지키는 것이다.

1. 현재 작업과 관련된 정보를 제공한다.
2. 오래되었거나 변경된 정보는 최신 상태로 갱신한다.
3. 확인된 사실과 추측을 구분한다.
4. 서로 충돌하는 정보가 있다면 어느 정보가 최신인지 명시한다.

## 4. 실습 1 - Context에 따른 답변 비교

Unity 게임에서 플레이어 공격 애니메이션이 재생되지 않는 상황을 가정하고 두 가지 프롬프트를 비교했다.

### Prompt A

```text
Unity에서 플레이어 공격 애니메이션이 재생되지 않아.
원인을 분석하고 해결 방법을 알려줘.
```

### Prompt B

```text
Unity 6과 C#으로 2D 게임을 개발하고 있어.

플레이어가 공격 버튼을 누르면
Animator의 Attack Trigger를 설정하도록 구현했어.

그런데 공격 애니메이션이 재생되지 않는 문제가 있어.

실제 코드와 Animator 설정 정보는 아직 제공하지 않았으니
원인을 확정하지 말고 가능한 원인과 확인 방법을 알려줘.

추가 정보가 필요하다면 어떤 정보가 필요한지도 알려줘.
```

### 실습 결과

두 프롬프트 모두 생각보다 좋은 답변을 제공했다.

**Prompt A의 결과**

- 입력 처리 문제
- Animator 파라미터 문제
- Transition 설정 문제
- Animation Clip 문제

등을 원인 후보로 제시했다.

또한 공격 코드와 Animator 설정 화면이 필요하다고 요청했다.

**Prompt B의 결과**

- 입력 처리 여부
- Attack Trigger 설정 여부
- Animator Transition 조건
- 다른 애니메이션에 의한 상태 변경 가능성

등을 구분해서 설명했다.

실제 코드와 설정 정보가 없다는 점을 고려해 원인을 단정하지 않았고, 필요한 자료도 요청했다.

### 실습을 통해 느낀 점

두 답변 모두 유용했기 때문에 Context를 상세하게 제공하는 것이 항상 압도적으로 좋은 결과를 만드는 것은 아니라는 점을 확인했다.

최근 AI 모델은 간단한 요청만으로도 사용자의 의도를 어느 정도 파악하고 필요한 정보를 되물어볼 수 있다.

따라서 처음부터 모든 정보를 완벽하게 작성하기보다는 자연스럽게 질문하고, 답변이 부족할 때 필요한 정보를 추가하는 방식도 충분히 효율적이라고 생각했다.

## 5. 실습 2 - AI가 필요한 정보를 질문하도록 하기

이번에는 AI가 원인을 바로 추측하는 대신, 문제 해결에 필요한 정보를 먼저 질문하도록 했다.

사용한 프롬프트는 다음과 같다.

```text
Unity 6과 C#으로 2D 게임을 개발하고 있어.

플레이어 공격 애니메이션이 재생되지 않는 문제가 발생했어.

아직 코드와 Animator 설정은 제공하지 않았어.

바로 원인을 추측하거나 해결 방법을 제시하지 말고,
문제를 분석하기 위해 필요한 정보를 먼저 질문해 줘.

한 번에 질문을 하나씩만 해줘.
```

AI는 입력 시스템, 입력 설정 방식, Action Type과 Binding 등의 정보를 순서대로 질문했다.

하지만 실제로 진행해 보니 질문이 지나치게 세분화되는 느낌이 있었다.

개발 과정에서는 관련 코드와 Input Actions 설정 화면을 함께 제공하고, 전체적인 흐름을 분석해 달라고 요청하는 편이 더 효율적일 것 같았다.

### 실습을 통해 느낀 점

AI가 질문을 많이 한다고 해서 반드시 문제 해결에 효율적인 것은 아니다.

필요한 정보를 확인하는 과정도 중요하지만, 질문을 지나치게 잘게 나누면 오히려 작업 시간이 길어질 수 있다.

따라서 상황에 따라 다음과 같은 방식을 선택하는 것이 좋겠다고 생각했다.

- 문제가 단순하다면 자연스럽게 질문하고 답변을 확인한다.
- 코드나 설정이 필요한 문제라면 관련 자료를 함께 제공한다.
- 정보가 부족하다면 AI가 필요한 내용을 질문하도록 한다.
- 질문이 반복되거나 비효율적이라면 필요한 정보를 한 번에 제공한다.

## 6. 프로젝트 Context와 대화의 연속성

이번 학습에서 개인적으로 가장 흥미로웠던 부분이다.

과거 Angvik Returns를 개발할 때 ChatGPT와 긴 대화를 이어가면서 개발을 진행한 경험이 있다.

매번 새로운 대화를 시작하기보다는 기존 대화에서 코드와 오류를 공유하고, 이전에 진행했던 작업을 바탕으로 다음 문제를 해결하는 방식이었다.

당시에는 대화가 길어져도 큰 불편함 없이 개발을 진행할 수 있었다.

그 이유는 무엇일까?

### 6-1. 대화 Context

현재 대화에서 주고받은 내용은 다음 답변을 생성할 때 참고할 수 있다.

예를 들어 다음과 같은 정보가 대화에 쌓일 수 있다.

- 프로젝트의 개발 환경
- 기존 코드와 수정된 코드
- 발생했던 오류
- 이전에 시도한 해결 방법
- 이미 확인한 문제와 아직 확인하지 못한 문제

이러한 정보가 유지되면 매번 프로젝트 상황을 처음부터 설명할 필요가 줄어든다.

다만 대화가 길어진다고 모든 내용이 항상 동일한 비중으로 활용되는 것은 아니다. Context Window의 제한이나 정보의 관련성에 따라 필요한 내용이 충분히 반영되지 않을 수도 있다.

### 6-2. Memory와 Context의 차이

Memory와 Context는 비슷해 보이지만 구분할 필요가 있다.

| 구분 | Context | Memory |
|---|---|---|
| 의미 | 현재 작업에 필요한 정보 | 대화를 넘어 참고할 수 있는 장기적인 정보 |
| 주요 내용 | 코드, 오류, 현재 작업, 최근 결정 | 사용자 선호, 프로젝트의 주요 특징 |
| 활용 목적 | 현재 문제 해결 | 이후 대화에서 배경 정보 활용 |

예를 들어 Angvik Returns 프로젝트의 ResourceManager와 PoolManager를 사용했다는 사실은 장기적인 프로젝트 정보로 참고할 수 있다.

하지만 이것이 현재 프로젝트의 모든 소스 코드와 최신 구현 상태까지 기억하고 있다는 의미는 아니다.

따라서 실제 코드 분석이 필요하다면 최신 코드를 다시 제공하거나 프로젝트 파일을 참고하도록 해야 한다.

## 7. 프로젝트 Context 문서 관리

프로젝트가 커지고 AI와 함께 작업하는 기간이 길어지면 대화 기록에만 의존하는 방식에는 한계가 있다.

이를 보완하기 위해 프로젝트의 주요 정보를 별도의 문서로 관리하는 방법을 학습했다.

예를 들어 GitHub 프로젝트에 다음과 같은 문서를 둘 수 있다.

### PROJECT_CONTEXT.md

프로젝트의 전체적인 정보를 정리하는 문서다.

```text
# Project Context

## Project Overview
- 프로젝트 이름
- 프로젝트 목적
- 게임 장르

## Development Environment
- Unity Version
- Programming Language
- 사용 중인 주요 패키지

## Team
- 팀 구성
- 각자의 담당 업무

## Major Systems
- PlayerController
- Inventory
- PlayerEquipment
- ResourceManager
- PoolManager

## Resource Management
- Addressables 사용 여부
- 리소스 로딩 및 해제 방식
- Object Pooling 구조

## Current Status
- 현재 개발 단계
- 완료된 기능
- 진행 중인 작업
- 알려진 문제
```

### 함께 관리하면 좋은 문서

| 문서 | 목적 |
|---|---|
| PROJECT_CONTEXT.md | 프로젝트 전체 정보 |
| CODING_RULES.md | 코드 작성 규칙과 설계 원칙 |
| CURRENT_STATUS.md | 현재 개발 상황과 남은 작업 |
| CHANGELOG.md | 주요 변경 사항 기록 |
| README.md | 프로젝트 소개와 실행 방법 |

모든 문서를 처음부터 만들 필요는 없다.

프로젝트 규모와 작업 방식에 맞춰 필요한 문서부터 관리하면 된다.

핵심은 AI가 프로젝트의 전체적인 구조와 현재 상태를 파악할 수 있도록 정보를 정리해 두는 것이다.

## 8. Context Handoff - 새로운 대화로 작업 이어가기

긴 대화가 항상 좋은 것은 아니다.

대화가 길어지면서 이전 코드와 최신 코드가 혼재하거나, 과거에 사용했던 해결 방법이 현재 상황과 맞지 않을 수도 있다.

이럴 때는 새로운 대화를 시작하면서 필요한 정보를 전달하는 방법이 있다.

이를 Context Handoff라고 이해했다.

새로운 대화에서 다음과 같은 정보를 제공하면 된다.

1. 프로젝트 개요
2. 현재 작업하려는 내용
3. 관련 코드와 설정
4. 지금까지 시도한 방법
5. 확인된 사실과 발생한 문제
6. 아직 해결되지 않은 부분
7. 유지해야 할 조건이나 제약 사항

### Context Handoff 예시

```text
[프로젝트 개요]
Unity 6과 C#으로 2D 액션 게임을 개발하고 있어.

[현재 작업]
플레이어 공격 애니메이션이 재생되지 않는 문제를 해결하고 싶어.

[현재 구현]
공격 버튼을 누르면 Animator의 Attack Trigger를 설정하고 있어.

[확인한 내용]
- 입력 시스템은 New Input System 사용
- Input Actions 에셋을 Inspector에서 연결
- 공격 입력이 발생하는지 확인 중

[문제 상황]
공격 버튼을 눌러도 애니메이션이 재생되지 않아.

[제공할 자료]
- PlayerController 코드
- Input Actions 설정 화면
- Animator 상태 및 Transition 설정 화면

[요청 사항]
전체 입력부터 애니메이션 재생까지의 흐름을 분석해 줘.
확인된 사실과 추측을 구분하고,
원인이 확실하지 않다면 추가 정보를 요청해 줘.
```

이렇게 정리하면 이전 대화의 모든 내용을 다시 전달하지 않아도 현재 작업에 필요한 맥락을 제공할 수 있다.

## 9. AI와 함께 개발할 때의 Context 관리 흐름

지금까지 학습한 내용을 실제 개발 과정에 적용하면 다음과 같은 흐름으로 정리할 수 있다.

1. **초기 Context 제공**: 프로젝트 환경과 주요 시스템을 설명한다.
2. **작업별 Context 제공**: 현재 작업과 관련된 코드, 오류 로그, 설정 정보를 제공한다.
3. **변경 사항 갱신**: 코드나 설계가 변경되면 최신 상태를 AI에게 전달한다.
4. **결과 검증**: AI가 제안한 해결 방법을 실제 코드와 실행 환경에서 확인한다.
5. **변경 사항 기록**: 확인된 해결 방법과 주요 변경 사항을 문서에 반영한다.
6. **새로운 대화로 연결**: 필요하다면 Context Handoff를 통해 다음 작업을 이어간다.

이 과정에서 Git을 함께 활용하면 코드 변경 이력을 관리하고, AI에게 최신 코드와 변경 사항을 전달하기도 쉬워진다.

## 10. Day 4 학습 정리

이번 학습을 통해 Context Engineering은 단순히 프롬프트에 많은 정보를 추가하는 기술이 아니라, AI가 현재 상황을 정확하게 이해할 수 있도록 필요한 정보를 선택하고 관리하는 과정이라는 점을 이해했다.

특히 다음 세 가지를 중요하게 생각하게 되었다.

**첫째, 처음부터 완벽한 프롬프트를 작성할 필요는 없다.**

자연스럽게 질문하고 AI의 답변을 확인한 뒤, 부족한 정보가 있다면 추가로 제공하는 방식도 충분히 효율적이다.

**둘째, 대화의 연속성은 AI 활용에 도움이 된다.**

이전 대화에서 공유한 코드, 오류, 결정 사항 등이 유지되면 같은 내용을 반복해서 설명할 필요가 줄어든다. 다만 이전 정보가 최신 상태인지 확인하는 과정도 필요하다.

**셋째, 프로젝트 정보를 별도로 관리하는 것이 중요하다.**

프로젝트가 커질수록 대화 기록에만 의존하기 어렵다. 프로젝트 개요, 코드 작성 규칙, 현재 상태, 변경 이력 등을 문서로 관리하면 새로운 대화에서도 작업을 이어가기 쉬워진다.

결국 AI를 잘 활용하려면 질문하는 방법뿐 아니라, AI가 참고할 수 있는 정보를 어떻게 관리할지도 고민해야 한다.

## 11. 추가 학습 방향 - AI 답변 검증의 중요성

이번 학습을 진행하면서 AI를 활용하는 능력만큼 AI가 제공한 답변을 검증하는 능력도 중요하다고 생각했다.

AI는 자연스럽고 논리적으로 보이는 답변을 제공하지만, 실제로는 잘못된 정보나 실행되지 않는 코드를 생성할 수도 있다.

따라서 AI의 답변을 무조건 신뢰하기보다는 결과가 실제로 올바른지 확인하는 과정이 필요하다.

앞으로 AI 프로젝트를 진행하면서 다음과 같은 내용을 추가로 학습하고 싶다.

- **정보 검증:** 공식 문서와 신뢰할 수 있는 자료를 통해 AI 답변의 사실 여부 확인하기
- **코드 검증:** 생성된 코드를 직접 실행하고 테스트하여 예상한 대로 동작하는지 확인하기
- **답변 평가:** 테스트 데이터와 평가 기준을 만들어 AI 답변의 정확성과 품질 비교하기
- **오류 대응:** 환각이나 잘못된 전제가 포함된 답변을 발견하고 개선하는 방법 익히기
- **지속적인 품질 관리:** 프롬프트나 모델이 변경되었을 때 기존 답변의 품질이 유지되는지 확인하기

특히 AI에게 자신의 답변을 다시 검토하도록 요청하는 방법과 실제 테스트 결과를 활용하는 방법의 차이도 학습하고 싶다.

앞으로는 AI API를 활용한 프로그램을 만드는 것에서 끝내지 않고, **AI가 생성한 결과를 어떻게 평가하고 검증할 수 있을지**까지 고민하며 프로젝트를 진행할 예정이다.
